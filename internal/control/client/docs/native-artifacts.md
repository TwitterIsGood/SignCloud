# Native libraries and project prerequisites

## The worker runs Xcode, not your build scripts

For `xcode` and `simulator` builds the worker runs `xcodebuild` against the uploaded source. It
does not run `cargo`, `pod install`, `npm install`, custom Makefiles, arbitrary shell scripts, or
download toolchains. `expo` is the exception: it installs JavaScript dependencies, runs Expo
prebuild and CocoaPods before archiving. The only other allow-listed action is
`xcodegen generate`, and only when the worker administrator enabled it and the project has
`project.yml` without a generated Xcode container.

A target that links a local static library, `.xcframework` or vendored framework must find it
inside the source bundle. The usual failure is:

```
ld: library 'poki_launcher' not found
```

That means the artifact was never built or never uploaded — not that the worker needs a new flag.
Build it on the caller side for the device platform, place it at the path the Xcode project
links, and upload the result:

```bash
# Example: a Rust static library consumed by an iOS target.
native/launcher/build.sh   # writes native/launcher/target/aarch64-apple-ios/release/libpoki_launcher.a
```

Build for `aarch64-apple-ios` (device) and, if the project also runs in the Simulator, for the
simulator slice or an `.xcframework` covering both. Ship the final archive only; keep
intermediates such as a Cargo `target/` tree out of the upload, and remember that directories
named `build`, `dist`, `DerivedData` and `node_modules` are excluded automatically (a `target`
directory is not).

## Keep generated Xcode projects in sync

Projects generated by XcodeGen or Tuist are uploaded as generated. If a setting lives both in a
spec (`project.yml`, `project-base.yml`) and in the generated `.xcodeproj`, changing only the spec
has no effect until the project is regenerated or the generated file is edited too. Verify the
value that actually reaches `xcodebuild` — for example a build setting such as an App Group — in
the `.xcodeproj/project.pbxproj` that is uploaded.

## Source archive rules

- Include the `.xcodeproj` or `.xcworkspace`, source files, resources, shared schemes, dependency
  manifests, lock files and any prebuilt binaries the targets link.
- Exclude `.git`, `node_modules`, `DerivedData`, `build`, `dist` and other generated output.
- For CocoaPods projects include `Podfile` and `Podfile.lock`; the workspace and required Pods must
  be available to the build.
- A Scheme used by an unattended build must be shared (`xcshareddata/xcschemes`).
- Signing stays automatic where possible; remove hard-coded provisioning profiles and identities.
